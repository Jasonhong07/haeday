## 1. 1단계 · 결제·환불 안전

### 공통 설계 변경
1. **환불 실행을 작업(queue)으로 분리.** 새 큐 `refund`(환불 행 ID별 1개). 환불 "의도"(refunds 행)는 주문 상태 변경과 같은 트랜잭션에 기록하고, Stripe 호출은 작업이 수행. 고객 화면처럼 즉시 결과가 필요한 곳은 커밋 후 같은 실행 함수를 한 번 직접 호출(멱등 키가 같아 중복 환불 불가).
2. **Stripe를 기준값으로.** 환불 웹훅을 받으면 이벤트 본문 대신 Stripe에서 환불과 charge를 다시 조회해 현재 상태·누적 환불액으로 반영(이벤트 순서 문제 제거).
3. **`payment_issues` 테이블 신설.** 사람이 봐야 하는 결제 이상(검증 실패, 대사 차이, 36시간 지연)을 모아 관리자 화면 "조치 필요"에 표시하고 관리자 메일 1통 발송.
4. **마이그레이션 `0001`** (한 번에):
   - `refunds`: `attempt_no`, `last_checked_at`, 사유에 `validation_failure` 추가
   - `orders`: `discount_cents`, `promotion_code`, `checkout_expires_at`, `delivery_promise`('minutes'|'24h')
   - `readings`: `library_version`, `first_viewed_at`
   - `generation_attempts`: `input_tokens`, `output_tokens`
   - `chart_revisions`: `first_viewed_at` · `guests`: `first_touch`(jsonb, 길이 제한)
   - 신규: `payment_issues`, `marketing_contacts`(3단계), `email_outbox.priority`·`category`

### F1 · 생성 실패 후 환불 누락 (2A)
- **현재:** `failAndRefund`가 주문을 failed로 저장한 뒤 별도로 환불 요청 → 사이에서 프로세스가 죽으면 환불 없는 결제 주문이 남음(재현됨).
- **변경:** 한 트랜잭션에서 ① 주문 `failed` ② 환불 행 `requested`(reason `service_failure`) ③ 주문 `refund_pending` ④ `refund` 작업 등록 ⑤ 사과 메일 outbox 등록. 커밋 후 Stripe 호출은 작업이 수행. 대사(15분)는 `requested` 행도 작업으로 재등록.
- **파일:** `fulfillment/generate.ts`, `payments/refunds.ts`(`claimRefundInTx`, `executeRefund`로 분리), `worker/index.ts`, `queue/boss.ts`.

### F2 · 환불 웹훅이 API 응답보다 먼저 도착 (2B)
- **변경:** Stripe 환불 생성 시 `metadata.refundRowId` 추가. 웹훅 처리 순서: `stripeRefundId`로 찾기 → 없으면 `metadata.refundRowId`로 우리 행 찾아 `stripeRefundId` 채움 → 둘 다 없을 때만 provider 행 생성. API 결과 저장은 "같은 ID면 통과, 상태는 전이 규칙대로".
- **테스트:** 재현 B + 웹훅이 먼저 와도 행 1개·예외 없음.

### F3 · 환불 상태·대사·재시도 (2C)
- **상태 규칙:** `requested/unknown → pending/requires_action → succeeded/failed/canceled`. `failed`·`canceled`는 종결. `succeeded`는 Stripe가 나중에 `failed`로 바꾸는 경우만 허용(돈이 우리에게 돌아옴 → 주문 paid 복귀 + `payment_issues`). 그 외 역행은 무시.
- **대사 대상:** `requested`·`unknown`(같은 멱등 키로 재호출) + 1시간 넘은 `pending`·`requires_action`(Stripe 조회만, 새 요청 없음). 결제 연결부에 `getRefund`, `getChargeRefundTotal` 추가.
- **재시도 구분:** 불확실(unknown) = **같은 키** 재시도. 확정 실패 후 새 환불 = `attempt_no + 1`, 키 `refund:{order}:{attempt}`. 부분 유니크 인덱스는 종결 실패 행을 제외하므로 새 시도가 가능.
- **부분 환불:** 주문 상태는 charge의 **누적** `amount_refunded`로 판단(전액이면 refunded).
- **테스트:** 재현 C1–C5 + "succeeded 후 늦은 pending 무시", "succeeded → failed 역전 처리".
- **ChatGPT 확인:** Stripe 환불이 succeeded 후 failed가 되는 경우의 처리(주문 paid 복귀)가 맞는가?

## 4. 4단계 · 출시 준비
- 운영 환경을 **테스트 키로** 먼저 생성 → 스모크 테스트(명식, 결제 4242, 풀이, 메일, 환불, 관리자).
- 복구 훈련: staging DB 백업 → 새 DB 복원 → 앱 연결 확인(ARCHITECTURE §8).
- 약관·개인정보처리방침 갱신: PostHog, 마케팅 메일·수신거부, 할인 코드·$0 주문 환불 불가, 24시간 지연 고지.
- 출시 체크리스트(Runbook §7) 증거 기록 → Jason이 `LIVE_PAYMENTS_APPROVED=true` 입력 시에만 live 전환(D08: 본인 카드 실결제 테스트 없음).

## 5. ChatGPT 교차검증 방식
- **CC0(지금):** 이 제안서 검증. 붙여넣을 요청문: `docs/review/CHATGPT_PROMPT_PROPOSAL.md`.
- **CC1–CC3:** 단계가 끝날 때마다 `docs/review/CHANGES_<날짜>_phaseN.md`(변경 요약·테스트 결과·확인 질문) + `.diff` 제공 → Jason이 ChatGPT에 붙여넣기 → 답을 저에게 전달 → 재현 후 반영(지금과 같은 절차).
- 규칙: ChatGPT 지적은 **재현 테스트로 확인한 뒤** 수정. 승인된 결정(D번호)을 바꾸는 지적은 Jason 확인 후에만.
