# Jason이 직접 해야 하는 출시 절차

갱신: 2026-09-26. 계정 셋업과 도시 데이터 입력은 완료했다고 전달받았다. 이미 한 가입을 반복하지 않는다. 아래는 본인 확인·비밀키 입력·콘텐츠 판단·사업자 답변처럼 에이전트가 대신 확정할 수 없는 부분만이다. 테스트 명령, 코드 수정, 증거 정리, 샘플 표 작성은 에이전트가 한다.

## 1. 한 번만 알려주면 되는 정보

1. Railway → Haeday 프로젝트 → web 서비스 → Settings → Networking의 생성 도메인 또는 연결 도메인을 연다.
2. 브라우저 주소의 **웹사이트 URL만** 채팅에 보낸다. Railway 변수 값, 로그인 링크, 키, 토큰은 보내지 않는다.
3. 운영과 staging이 둘 다 있으면 어느 것이 staging인지 함께 적는다.
4. 에이전트가 공개 페이지·보안 헤더·로그인 보호·도시 검색을 읽기 위주로 확인하고 실패를 수정한다. 계정 설정이 완료됐다는 사실과 앱 배포 검증 완료는 별도로 기록한다.

## 2. 비밀키가 필요한 경우만: 기존 Railway 설정 확인

1. Railway 프로젝트 → **web → Variables**를 연다. 비밀값을 채팅에 붙이지 않는다.
2. `APP_ENV`, `APP_ORIGIN`, `PAYMENTS_MODE=test`, `LIVE_PAYMENTS_APPROVED=false`, DB 연결이 해당 staging 환경인지 확인한다.
3. worker에도 공통 DB·암호화 키·AI·이메일 설정이 같은 환경으로 들어가 있는지 확인한다. 암호화 키를 새로 덮어쓰면 기존 데이터를 열 수 없으므로 임의로 재생성하지 않는다.
4. 아래 공급자가 이미 설정돼 있으면 새 키를 만들지 않는다. 빠진 이름만 에이전트가 체크리스트로 알려주게 한다. 상세 표는 `SETUP_PROVIDERS.md`를 쓴다.
5. 설정 저장으로 재배포가 발생할 수 있다. **production이 아니라 staging인지 먼저 확인**한다. live 전환은 7번 승인 때 별도로 한다.

| 용도 | 확인할 이름 | 사람이 해야 하는 부분 | 에이전트가 하는 부분 |
|---|---|---|---|
| Stripe 테스트 | STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET, STRIPE_PRICE_SAJU | Dashboard 테스트 환경에서 기존 값 확인·입력 | 웹훅 경로/이벤트·금액·재시도·환불 대사 검증 |
| PayPal sandbox | PAYPAL_CLIENT_ID, PAYPAL_CLIENT_SECRET, PAYPAL_WEBHOOK_ID | sandbox 앱과 구매자 계정 로그인/승인 | create/capture/중복/응답 유실/환불/CSP 검증 |
| AI | LLM_API_KEY, LLM_MODEL, LLM_DAILY_CAP | 기존 모델·과금 계정의 키 입력, 샘플 생성 비용 허용 | 5건 비용 측정·15개 품질 샘플 생성·결과표 작성 |
| 메일 | RESEND_API_KEY, EMAIL_FROM, SUPPORT_EMAIL | 도메인 소유 확인·DNS 권한·테스트 메일 실제 수신 | SPF/DKIM 상태/발신 흐름·만료 링크·재발송·반송 확인 |
| 관리자 | ADMIN_EMAILS | 받을 본인 이메일 설정, 매직링크 로그인 | 8단계 퍼널/매출·환불 원장 일치/보호 경로 확인 |
| 암호화 | ENCRYPTION_KEYS, ENCRYPTION_ACTIVE_KEY_ID, EMAIL_LOOKUP_KEY, SESSION_SECRET | 안전한 비밀 저장소의 백업 보관 | 형식·활성 키·암호화 저장·복원 검사 |

**본인 카드로 live 결제 테스트는 하지 않는다.** Stripe 테스트 카드는 공급자가 명시한 테스트 모드에서만 쓴다. 로컬 체험은 카드 번호가 필요 없다.

## 3. 콘텐츠 승인: 코딩보다 Jason의 판단이 필요한 부분

1. `CONTENT_REVIEW_KO.md`를 연다. 72개 초안의 한국어 의미를 검토한다.
2. 문제가 있는 항목 ID와 바꿀 취지만 알려준다. 에이전트가 문장을 고치고 diff를 만든다.
3. 승인한 항목 또는 전체 승인을 채팅에 명시한다. 에이전트가 승인 메타데이터를 반영한다. 동의가 없는 항목에 이름을 넣지 않는다.
4. 에이전트가 실제 모델로 15개 샘플을 만든 뒤, Jason은 별도 평가표에서 자연스러움·도움·과장 여부를 판단한다. 기존 기준: **12/15 이상 합격, 사실/위험 오류 0건**.
5. 랜딩의 가상 인물 샘플도 따로 확인한다. SEO 해석 가이드는 승인 전 비공개로 유지할 수 있으므로 출시를 위해 전부 검토할 필요는 없다.

## 4. 본인 이메일로 관리자 화면 확인

1. staging의 `/login` → ADMIN_EMAILS에 넣은 주소 입력 → 메일 수신.
2. 링크를 열어 확인 버튼을 누른다. 메일 스캐너의 자동 클릭만으로 로그인되지 않아야 한다.
3. `/admin`에서 방문→입력 시작→명식 생성→무료 명식 열람→결제 시작→결제→풀이 전달→풀이 열람의 **8단계**가 보이는지 확인한다.
4. 날짜 범위를 바꾼다. 방문자 수와 주문 수는 같은 단위가 아니므로 차이가 있다는 이유만으로 오류라 단정하지 않는다. 에이전트가 DB와 대조한다.
5. 판매 중지·환불 버튼은 실서비스에서 시험 삼아 누르지 않는다. staging 테스트 주문에서 에이전트와 함께 확인한다.

## 5. 답변이 아직 필요한 사업 운영 항목

여기는 법률·세무 결론을 에이전트가 승인할 수 없는 부분이다. 기존 결정을 바꾸라는 요청이 아니다.

1. **Stripe:** 본인 계정으로 Support에 로그인 → 한국 이주 후 미국 개인사업자 계정 운영/주소/은행/세금정보에 관한 서면 답변 요청. 기존 Runbook 영어 템플릿을 사용한다. 서면 답변에서 키·개인정보를 가린 내용만 공유한다.
2. **OPT/회사:** 현재는 initial OPT라는 D05를 유지한다. EAD 기간·학위 관련 업무·보고 요건을 DSO에, 입사 후 겸업 승인을 회사에 확인한다. STEM 연장 승인으로 간주하지 않는다.
3. **CPA:** 판매세 징수·상품 분류·신고·이주 후 세무 처리의 답변을 받는다. Tax 스위치가 꺼져 있다는 것만으로 적법성 확인이 완료되지는 않는다.
4. **법적 페이지:** 실제 판매자/지원 주소·보유기간·환불 문구를 확인하고 승인한다. 초안 표시를 에이전트가 임의로 없애지 않는다.
5. **환불 실패 D49:** ‘다른 카드로 Stripe 환불’은 그대로 구현하지 않는다. 제공자 확정 실패 후 수동 해결 수단을 합의하고, 무료 풀이를 고객의 선택으로만 제안하는 수정안에 대한 Jason 답변 대기.

## 6. 마케팅 관련 판단은 출시 핵심 경로와 분리

- 이미 있는 Instagram/TikTok/YouTube 계정 핸들만 알려주면 프로필·콘텐츠 연결 작업을 준비할 수 있다. 새 계정 가입·게시·유료 플랜은 자동 실행하지 않는다.
- 우편 주소 적법성/이용 동의가 확인되기 전 마케팅·이탈 복구 이메일을 켜지 않는다. 거래 메일은 별도 검증 가능하다.
- 디자인 선호 답변이 없어도 현재 승인 브랜드(밤색 배경·달·금색·한지)를 유지해 개발했다. 첫 방문자 화면을 보고 필요한 수정만 알려주면 된다.

## 7. 마지막 출시 승인

1. 에이전트가 테스트/AI 품질/실제 공급자 sandbox/메일/복원/콘텐츠/문구 체크를 한 장으로 정리한다.
2. 미확인·차단 항목을 보고 **staging 변경 승인**과 **production 배포/live 승인**을 구분해서 말한다.
3. production도 처음에는 TEST 키로 확인한다. DB 복원은 반드시 분리된 복원 대상에 하며 운영 DB를 덮어쓰지 않는다.
4. 모든 증거가 갖춰지면 live 전환을 명시적으로 승인한다. 첫 실제 고객 주문을 확인하며, 자기 카드 결제를 검증 방법으로 쓰지 않는다.

Jason에게 명령어 실행·로그 해독·문서 재복사를 시키지 않는다. 연결 가능한 계정/작업공간이 있으면 에이전트가 나머지를 진행하고, 없으면 필요한 접속 위치만 질문한다.
