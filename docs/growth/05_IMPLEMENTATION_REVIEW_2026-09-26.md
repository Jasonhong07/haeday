## 3. 남은 문제: 확정과 검토 가설을 구분

### R1 · 출시 전 · D49의 환불 방식 표현 수정 필요 (사용자 답변 대기)

현재 결정의 ‘다른 카드로 환불’은 Stripe Refunds API의 동작과 맞지 않는다. Stripe는 원 결제수단에만 환불하며, 실패 확정 때 별도 반환 방법을 마련하도록 안내한다.

- 제안: 원 환불의 최종 실패 확인 → 고객과 대체 반환 방법 합의 → 관리자 수동 지급 기록 및 증빙 → 이중 반환 방지. 무료 풀이는 고객이 선택한 대안으로만 취급.
- Stripe API의 `refunded`와 외부 수동 정산을 같은 사실로 덮어쓰지 않는다. 별도 상태/원장 필요 여부를 설계 후 검토.
- D49는 승인된 결정이므로 임의 변경하지 않았다. 사용자에게 확인 요청했다.
- 공식 근거: [Stripe refund destinations / failed refunds](https://docs.stripe.com/refunds#refund-destinations), 확인 2026-09-26.

### R2 · 출시 전 · PayPal 실 SDK 검증 공백 (확정된 미검증)

테스트 키가 준비되면 Claude가 자동/수동 실행할 묶음:
1. 실제 sandbox create → 승인 → capture → delivered.
2. 승인 취소, 자금원 거절 후 재선택, SDK 로딩 차단, capture 응답 유실 후 주문 복구.
3. SDK `onError`가 승인/청구 뒤 도착해도 ‘청구 없음’으로 표시하지 않는지.
4. 실제 웹훅 서명 검증·중복·지연·역순, 웹훅 누락 대사.
5. 전액 환불, 환불 pending/failed, 분쟁, Stripe Tax 켰을 때 버튼 숨김.
6. CSP enforce에서 SDK iframe/popup/connect가 실제로 작동하는지. Venmo 노출은 실제 지원 환경에서 별도 확인.

임의의 실제 카드 구매 금지. 키는 채팅/문서에 적지 않는다.

### R3 · 출시 전 · 캡처와 주문 닫기의 경합 (검토 가설, 버그 확정 아님)

`captureAndApply`는 주문 open 조회 후 외부 capture를 호출한다. 사이에 다른 경로가 주문을 닫을 수 있으므로 ‘닫힌 주문은 절대 청구하지 않는다’는 주석만으로 경쟁 상황이 사라지지 않는다. D51의 late-payment 처리로 안전할 수 있으나 추가 증거가 필요하다.

재현 테스트: open 조회 완료 → capture 직전 대기 → 형제 주문 결제/원 주문 닫기 → capture 성공 → 결과 적용. 기대: 돈이 사라지지 않고 정확히 한 풀이를 제공하거나 중복 결제 환불 의도를 원자적으로 기록. 사용자 화면이 ‘아무것도 청구 안 됨’이라 오도하지 않아야 한다. **외부 API 호출을 DB 트랜잭션 안에 넣는 방식으로 고치지 않는다.**

### R4 · 운영 복원력 · 공개 랜딩의 불필요한 키 의존 (코드에서 확인, 장애 재현 미실행)

`page.tsx`가 `serverContext()`를 호출하므로 공개 설명 페이지에서도 DB 설정/암호화 키 로딩이 필요하다. 키링 주석의 ‘공개 페이지는 계속 작동’과 차이가 있다.

제안: 공개 랜딩의 판매 가용성 조회를 private context에서 분리하고, 조회 실패는 판매 불가로 안전하게 표시하되 설명 페이지는 렌더. broad catch로 잘못된 운영 설정을 감추지 말고 비식별 운영 경고를 기록. 테스트: 키 누락·DB 장애 시 랜딩은 200, 유료 진행은 차단, 경고는 남음. 이번 UI 작업에서 서버 가용성 계약을 임의 변경하지 않았다.

### R5 · 문서 최신화 (확정)

STATUS 상단이 CC0/197개 테스트 기준이었다. 현재 인계 요약을 추가하고 과거 내용은 역사적 기록으로 표시했다. 최종 통합 담당자는 CC4 전체 증거를 실제 실행 결과로 갱신해야 한다. ‘70%/80%’ 대신 **코드 구현 / 로컬 검증 / staging 검증 / 사업·콘텐츠 승인**을 나눠 관리한다.

## 4. 다음 UI/UX 개발 순서

### UX-A · 무료 명식 → 결제 전환 (먼저)
- 결과 첫 화면: Day Master 이름 → 승인된 2–3문장 → 오행 → 세부 명식. 모르는 전문용어는 짧은 설명으로 펼친다.
- 시간 불확실성과 입력 수정은 결제 CTA 바로 위에서 확인 가능해야 한다. 장식 카드가 안내를 가리면 안 된다.
- 유료 구성은 기존 OFFER_ITEMS를 재사용해 무료/유료 문구가 어긋나지 않게 한다. 미승인 문구는 가짜 예시로 채우지 않는다.
- 유료 원문을 브라우저에 보내 blur만 적용하는 잠금 금지. 서버 접근 제어 유지.
- 완료 증거: 360px·200% 확대·시간 모름/경계 질문·판매 중지·이미 구매 상태.

### UX-B · 결제·대기·복구
- 입력 확인 → 결제 전 동의 → 결제수단의 시각적 순서. PayPal 이메일과 카드 이메일의 역할을 혼동시키지 않는다.
- ‘확인 중 / 풀이 생성 중 / 전달됨 / 환불 요청 중 / 환불 완료 / 조치 필요’를 고객 언어로 분리.
- 재결제보다 주문 상태 확인을 우선. 환불 요청 성공을 은행 입금 완료로 표현하지 않는다.
- PayPal 로딩 중·SDK 차단 시 카드 경로를 유지하고, 불확실한 청구 상태에서는 새 결제를 권하지 않는다.

### UX-C · 유료 풀이 독서 경험
- 한지 배경, 본문 17–18px, 1.7–1.8 line height, 모바일 20px 좌우 여백.
- 섹션 목차와 현재 위치, 글자 크기 선택. 고정 막대가 본문/키보드 포커스를 가리지 않도록 한다.
- 2027은 이미 기본 가격에 포함. 별도 추가 결제 유도 금지.
- ‘왜 이 설명인가’ 근거 보기(K1)는 섹션별 근거 매핑 계약을 먼저 승인받은 뒤 개발. snippet ID 존재만으로 해석의 타당성을 보증하지 않는다.

### UX-D · 공유와 측정
- 공개 공유 카드는 허용된 필드만: Day Master/승인 짧은 문구/브랜드 링크. 생년월일·시각·도시·이메일·주문 ID·풀이 본문 금지.
- 다운로드/공유 클릭과 실제 공유 성공을 다른 지표로 취급.
- 현재 first-party 8단계 퍼널을 우선 사용한다. **PostHog 신규 가입은 현재 출시 필수 작업이 아니다.**
- 랜딩→입력 시작→차트 생성→무료 결과 열람→checkout→paid→delivered→opened. 같은 cohort와 기간 활동을 섞지 않는다. $0 쿠폰은 매출·유료 전환에서 분리.

## 5. 디자인과 유입을 연결하는 실행안

기존 `01_DESIGN.md`, `02_MARKETING.md`, `03_COMPETITORS_FEATURES.md`는 근거·대본·전략 자료다. 다음 생산 작업은 Claude 또는 Codex가 수행하고 사용자가 파일을 복사/가공하도록 시키지 않는다.

1. 이번 카드 톤으로 세로 영상 표지 3종과 공유 카드 템플릿 1종 제작.
2. 영어 무음 Shorts 5개를 초안으로 렌더: ‘사주란 무엇인가’, ‘시간 몰라도 되는가’, ‘별자리와 다른 점’, ‘다섯 원소’, ‘무료 명식 보는 법’. 승인 문구만 활용.
3. 같은 원본을 플랫폼별 자막/길이/링크 동선에 맞춰 변환. 음악·이미지 라이선스 확인. 게시 전 사용자 검토.
4. 첫 14일은 영상 수보다 프로필 클릭→사이트 유입→무료 차트 생성→유료 전환을 본다. 조회수만 높으면 성공으로 판단하지 않는다.
5. 한국어/일본어/스페인어 제품을 만들기 전에 영어 퍼널을 검증. 바이럴과 매출은 보장하지 않는다.

공개 인기 디자인과 리뷰 관찰은 구매전환 증거가 아니다. 기존 문서의 출처·표본 한계를 유지한다. 이번 변경은 원본 CSS 일러스트이며 다른 디자이너의 이미지를 복제하지 않았다.
